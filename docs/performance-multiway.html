Idle

Nothing happens; what a window costs while it sits there. The caret blinks in the first seconds of a chat; the last window is after it has stopped.

Incoming messages

Five messages a second arrive in the open chat of a 20,000-message thread.

Scrolling

Mouse-wheel turns every 16 ms for 8 s up and 8 s down in the long thread.

Switching chats

100 selections of ten different chats, 80 ms apart.

Typing

80 real key presses through the display, 66 ms apart, into the message field.

Panels

The details panel of a 500-member group, then the media panel of the long chat, three times.

Resize

Six window sizes in a row, 0.5 s apart.

Startup

From starting the process to the harness answering, and to the chat list having its conversations (the mock itself waits two seconds to link, alike for all ways).

Catching up with a backlog

The mock sends a backlog of messages in one burst before it says it has synced. The snapshot times are how long the window did not respond.

Soak

Messages keep arriving for the soak time; the slope is a least-squares fit over the second half of the memory samples.

Frame pacing

The scrolling and an idle chat again, in separate runs with the Wayland requests logged (the logging costs processor time: these CPU numbers are not the others'). Gaps are between buffer commits of the window.

Memory

RSS is what the process holds in RAM (shared libraries included, which is why Qt's file-backed part is large); anonymous is its heap. VRAM and GTT are read from the drm client's fdinfo. The stacks use the medians of each part, so a stack's total is the median RSS plus the median GPU memory.

  • Anonymous (heap)
  • File-backed (shared libraries, mapped files)
  • GPU video memory (VRAM)
  • GPU shared memory (GTT)

Threads and binary size

Threads are counted in /proc once the chat list is up. The binary is the file that was mounted into the container (a testbox-profile build with the harness, not the stripped release).

How it was measured

Each client is built as the testbox profile and started on the mock backend in a container of its own, in a private display (the cage compositor with a VNC output) that draws on the host's GPU through a render node. Nothing of the host's desktop is shown to or captured from the clients. The mock holds 200 chats, a 20,000-message thread, a 500-member group and 640-pixel pictures. Input is real: wheel turns and key presses through the display's VNC socket. Every number is a /proc or drm counter read before and after the phase (CPU time of the process, context switches, memory from smaps_rollup, GPU engine time and memory from the drm fdinfo of the client's descriptors). The order of the ways rotates from round to round so that a drifting machine is spread over all.

What the numbers cannot say

  • One machine, one GPU, one driver, one compositor: another setup can order the ways differently.
  • The mock has no network, no real Signal data and no real pictures from a camera; it measures the clients, not the service.
  • CPU is the whole process, all threads, in percent of one core; a way that moves work to the GPU shows it in GPU time and memory, not in CPU.
  • Wakeups are context switches of the process (voluntary and not), not hardware wakeups or power.
  • Qt on the CPU draws without the GPU, so its GPU numbers are zero by design; the file-backed part of its RSS includes the Qt libraries.
  • A few rounds give a median and a range, not a confidence interval. The whiskers are the smallest and the largest round.
  • Frame gaps come from separate runs with the request log on, which costs processor time; they say how evenly frames were committed, not how they looked.
  • Nothing here measures input latency, text quality or visual differences.

Caveats

  • Only 2 frames run(s) per way: medians of so few values are weak; the whiskers are all the spread there is.
